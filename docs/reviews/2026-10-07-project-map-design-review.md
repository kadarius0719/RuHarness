## Findings

### 1. High — The walk gives no include folder to headers included with angle brackets, so all three liblzg tools fail to compile
What: §3.1 step 3 finds each file's include folders "from its includes (the scanner's resolution, extended…)". The scanner deliberately skips `#include <…>`. Real projects include their own public headers that way: in liblzg, all three tools and `extra/lzgmini.c` use `#include <lzg.h>`; in lz4, `examples/frameCompress.c` and `examples/fileCompress.c` use `<lz4frame.h>`, `<lz4frame_static.h>` and `<lz4file.h>`. Built as written, `src/tools/lzg.c` gets no `-Isrc/include` and fails. The map would then show no tools for liblzg, the project the testing guide uses. The spike did not see this because it gave every folder to every file.
Evidence: `harness-scan/src/lib.rs`, `collect_includes`: "`<...>` system includes are system_lib_strings and deliberately skipped." `liblzg/src/tools/lzg.c:31: #include <lzg.h>`. `cc -c -w -O0 src/tools/lzg.c` fails with "fatal error: 'lzg.h' file not found".
Suggested change: Step 3 should say that angle-bracket includes are resolved too. They search only the candidate folders, never the including file's own folder. When no candidate folder holds the header, it is left to the system. Add a test: a fixture whose tool includes `<proj.h>` from a sibling `include/` folder.

### 2. Medium — Step 3 does not say which folder wins when two hold the same header name, or when a project header shadows a system one
What: "Every folder that holds a .h is a candidate -I" says nothing about which candidate wins when two folders hold the same name (two `config.h`, a `win32/config.h` beside a generated one); in what order the folders are tried; whether a header's own includes are followed (a header in `lib/` that includes one in `common/`). The spike gave every file every folder, sorted alphabetically. That makes `programs/` a search folder for every file, and lz4's `programs/util.h` has the same name as the macOS SDK's `util.h`. A stray `config.h` elsewhere in the tree would also defeat §6's promise: a file needing a generated `config.h` would compile quietly with the wrong one, and the map would report no failure.
Evidence: `lz4/programs/util.h` shadows SDK `util.h`. §6: "the map says which files failed on a missing header and names it". Neither download has two headers with the same name, so this is not yet seen on real code.
Suggested change: Give a file only the folders its includes actually need, following headers' own includes too. When more than one candidate folder holds the header, record an "ambiguous include" fact listing all candidates; do not pick one; let `compile_commands.json` or the person's stated flags decide. Narrow the §6 claim to match.

### 3. Medium — The body still lets the walk guess the flags; the person's stated build has no place in the walk or the map file
What: §7 records that the person states the build and its flags, and the spike's list says "Flags are evidence the map must be given, not guessed". But the design's body has not caught up: §3.1 step 4 knows only `compile_commands.json`; §3.2's `flags_from` allows only `walk | compile_commands`; §6 treats `#ifdef` as a side residual; nothing records which named build the map is based on; each file gets one record with one set of flags (a shared file built with different flags for different tools cannot be shown); from `compile_commands.json` only `-I` and `-D` are taken, dropping `-include` (a forced `config.h`), `-U`, `-std` and `-iquote`/`-isystem`, and saying nothing about a file listed twice. As written, lz4's tool is mapped without threads and without `programs/util.c`, and nothing warns that a guess shaped it.
Evidence: Reran the spike. With `-DLZ4IO_MULTITHREAD -DNDEBUG`, `programs/lz4cli.c` gains `programs/util.c` and 12 outside symbols (11 `pthread_*` plus `sysctlbyname`). `-DNDEBUG` also removes `___assert_rtn` from 21 programs. Both configurations compile.
Suggested change: Add a step 4 source "person-stated named build". Make `flags_from` `compile_commands | stated:<build name> | walk-guess`. Add a top-level `configuration: {name, flags, source}`; mark every closure shaped by a guess `guessed_flags: true`. Key the per-file facts by (file, flags) so a file built two ways appears twice. Take the full list of compile flags that change the code (`-D -U -I -iquote -isystem -include -std`) and record the rest as ignored. Rename `defines`/`needs` to `defined_symbols`/`needed_symbols` (today `defines` reads as `-D` flags; §4's "changes a file's defines" already reads that way).

### 4. Medium — "Add all definers" plus §3.4's accounting rule refuses the right answer for liblzg, and collisions nobody needs are missed
What: Step 7 adds every definer of a duplicate to the closure. On liblzg that puts both `src/lib/decode.c` and `src/extra/lzgmini.c` into `unlzg` and `benchmark`. The design then lists `lzgmini.c` as shared by those two tools (step 8), which is not true once the duplicate is settled; and leaves `lzgmini.c` in none of §3.4's endings once the model correctly says "keep decode.c" (no longer in a tool's closure, step 9 did not make it unreached, not a test), so the correct reply "leaves one unaccounted for" and is "refused in full". Two related gaps: duplicates are only found while chasing needed symbols, so two closure files that both define a symbol nobody needs (a `ShowUsage` in the tool and in a library file pulled in for something else) are not reported, though the real link would fail with a duplicate-symbol error; and the spike's rule "a file that defines `main` is never pulled into another closure" is not in the design, while the spike's own form of that rule turns a symbol defined only in another program's `main` file into a fake outside symbol.
Evidence: design-faithful run gives `src/tools/unlzg.c ['src/extra/lzgmini.c','src/lib/checksum.c','src/lib/decode.c','src/tools/unlzg.c']`, `benchmark` the same plus `encode.c`. §3.4: "Every `.c` in the map must end in exactly one of: …". closure.py: `ds = [d for d in definers.get(s, []) if d not in mains or d == entry]` then `if not ds: outside.add(s)`.
Suggested change: Work out sharing after duplicates are settled; before then, mark duplicate definers "alternative, pending". Add the ending "alternative definer not kept" to §3.4; define "exactly one" so that one file can be in several tools. Find duplicates as every symbol defined by two or more files of the finished closure. Write down the `main`-file rule; a need met only by another program's `main` file becomes its own fact ("needs a symbol from program X"), never an outside symbol.

### 5. Medium — Only `main` makes an entry point, so lz4's fuzz driver becomes one 17-file program with a "which to keep" question
What: Step 6 knows only `main`. The 10 lz4 fuzzers are then not programs; they all sit inside `ossfuzz/standaloneengine.c`'s closure with a 10-way duplicate of `LLVMFuzzerTestOneInput`. §3.3 then asks the model "which definer to keep". The spike says that is the wrong question ("what is this?", not "which one?"). If the model picks one, that program links, and the check accepts a tool the project does not build.
Evidence: design-faithful run gives `standaloneengine` 17 files: lib×4, 10 fuzzers, `fuzz_data_producer.c`, `lz4_helpers.c` and itself. Spike: "the third is not a program."
Suggested change: Step 6 names three kinds of entry: `main`; fuzz target (`LLVMFuzzerTestOneInput`, with a closure from each); and "driver of many" (a `main` whose need is met by several entry files). A driver of many is recorded with the entries it serves and is never asked "which to keep". §3.2 gets `entry_points: [{path, kind}]`.

### 6. Medium — Reading `nm`: the symbol kinds named are incomplete, weak and common symbols mislead, and names differ between macOS and Linux
What: Step 5 says "external text, data and read-only symbols". Kinds left out: uninitialised globals (`B`), tentative definitions (`C`) and, on Linux, weak definitions (`W`/`V`); a global defined only in those forms would read as an outside symbol. Weak definitions: macOS `nm -g` shows a weak definition as a plain `T`; a weak default plus a strong override (a normal hook pattern) is reported as a duplicate and sent to the model, though the linker settles it every time. Weak undefined symbols: a reference to an optional weak symbol shows as plain `U` on macOS, so it becomes an outside symbol or pulls in an optional file; on Linux it shows as `w`, which the spike's reader ignores; the same project gets different closures on the two systems. Names: Mach-O puts `_` in front of every C name; the spike hard-codes `"_main"` and `"_LLVMFuzzerTestOneInput"`, so it finds no entry points on Linux; SCHEMAS says C symbol identity is "the linkage name for external symbols", while the scanner's facts carry `foo`, not `_foo`; the map's names would not join to the facts unless normalised.
Evidence: test `w1.c` shows `T _hook` both for `__attribute__((weak))` and for the strong `w2.c`; `nm -gm` shows "weak external _hook". `wu.c` shows `U _opt`, `nm -gm` shows "(undefined) weak external _opt". lz4 objects show `C _LZ4_cState`, `C _LZ4_streamHC` (common symbols on this Apple clang; gcc 10+ builds them as `B` by default). closure.py line 57: `"_main" in o["defs"]`.
Suggested change: Say exactly which symbols count as defined: text, data, read-only, bss, common, weak. Read weakness from the system's own `nm` output (`nm -m` on macOS; `W`/`V`/`w` on Linux); a weak and a strong definition of the same name is not a duplicate; a weak undefined symbol is an "optional" need, never an outside one. Remove exactly one leading `_` on Mach-O only, so the map's names equal the facts' names. Count common symbols with the same name in several files as one merged symbol, not a duplicate.

### 7. Medium — The optimisation level and C standard are not fixed, and the outside symbols depend on them
What: Step 5 gives `cc -c -w` with no `-O` and no `-std`. The spike used `-O0`. The judge builds at `-O2` with `-ffp-contract=off` (`cc_argv` adds `-O2` when no `-O` is given). On both downloads the closure files came out the same at -O0 and -O2, but the outside symbols differ in nearly every closure, and §3.4 guesses the libraries from those. At -O0, a C99 `inline` function in a header leaves a needed symbol that -O2 does not; that can pull in a different file or show a fake outside symbol. Each compiler also has its own default C standard (gcc 15 defaults to gnu23), so the same file can compile on one machine and fail on another.
Evidence: `lz4cli.c` at -O2 gains `_strcpy`, `_snprintf`, `_bzero` and loses `___strcpy_chk`, `___snprintf_chk`, `___memset_chk`; `examples/frameCompress.c` at -O2 loses `_fprintf`; test `inl.c` shows `U _sq` at -O0 and no reference at -O2; `harness-oracle/src/lib.rs` `cc_argv`: `argv.push("-O2".to_string())`.
Suggested change: Fix the map's compile flags in the design: the judge's `-O2 -ffp-contract=off`, or the stated build's own `-O`/`-std`. Record them in the map. Say that outside symbols are facts of that compiler and those flags, not of the source.

### 8. Medium — "Reproducible from the files alone" and "nothing here is macOS-only" are not true as written
What: §3.1 promises "every one reproducible from the files alone", but needed and outside symbols depend on the host's headers and on `#if defined(__APPLE__)` branches; whether a file compiles depends on the compiler's version; the link check cannot catch a missing `-lm` on macOS, because libm is part of libSystem there, so a map made on a Mac can pass a check that fails on Linux; §3.2 has no field for the compiler, the OS or the SDK (verdicts already record a `toolchain` for exactly this reason).
Evidence: lz4 `programs/timefn.c:61 #elif defined(__APPLE__) && defined(__MACH__)` needs `['_mach_absolute_time', '_mach_timebase_info']`; `programs/util.c` has `#elif defined(__APPLE__)` and `#elif defined(__linux__)` branches, needs here `['_sysctlbyname']`; SCHEMAS records verdicts' `"toolchain": ["rustc …", "Apple clang …"]`.
Suggested change: Reword to "reproducible from the files, the stated flags and the recorded toolchain". Add `toolchain: {cc: <first line of cc --version>, nm, target triple}` to the map. A map read under a different toolchain is shown as made elsewhere, as features and perf treat a changed compiler. Soften §6's Linux line to "runs on Linux; a map made on one platform describes that platform".

### 9. Medium — The limits contradict each other, do not exist where the design says, and a cut-short walk gives wrong closures
What: The documents disagree on what happens past the cap: §3.2 says "the map says so and the model step is not offered" (a partial map is written); §3.7 says exit 1 "refused (… limits)"; §4 says "refused by name". The limits do not exist in the scanner: step 1 says "the existing file-count and depth limits", but the scanner walks with `Limits::default()`, which has no limits; the only 20 000-file / depth-32 limit is the cockpit's file tree. The walk skips nothing by itself: `confined` does not skip `.git` or `migration/`; only `confined_except` with a list does. A cut-short walk gives wrong closures, not just short ones: the walk stops partway in sorted order, so definers in folders it never reached look like outside symbols. The 200 000-symbol cap has no stated unit. The scanner stops on the first bad entry: it returns an error on the first walk error and on any file that is not UTF-8, contradicting step 2's "recorded as such and kept", and §3.6 does not list the change.
Evidence: `harness-scan/src/lib.rs:133`: `walk::confined(&src_dir, &C_EXTENSIONS, walk::Limits::default())`, then `if let Some((path, why)) = walked.errors.first() { return Err(...)`, and line 164: `std::fs::read_to_string(abs).map_err(...)?`. `harness-tui/src/files.rs:22`: `max_files: Some(20_000)`, `max_depth: Some(32)`.
Suggested change: Choose one behaviour (suggested: past a cap, write only the file facts, compute no closures, exit 1 naming the limit). State the caps: which files count, the depth, the symbol unit (distinct names). Name `confined_except` with `.git`/`migration` skipped. Add to §3.6: the scanner keeps walk errors and non-UTF-8 files as facts instead of stopping.

### 10. Low — `root_hash` is not defined, and the ordering of the map's lists is not stated
What: `root_hash` is never defined in the docs or the code. SCHEMAS already has a "file-set hash" rule. The design should say which files it covers (`.c`/`.h` only, or also `compile_commands.json`, build files and set-aside sources) and that it does not cover the toolchain or the stated flags, which need their own fields; otherwise a stale picture is not "visibly stale" after a compiler change. The canonical serialization rule needs a sort order for every list (files by path bytes; `definers`, `outside`, `shared.tools` each sorted); closures stored as indexes into `files` only stay stable if that order is fixed. `taken_at_commit` is fine as long as nothing keys on it.
Suggested change: Define `root_hash` as the SCHEMAS file-set hash over every walked `.c`/`.h` plus `compile_commands.json` if present. Add a separate `inputs_hash` covering configuration plus toolchain. State the sort keys. Add a test that running the map twice gives a byte-identical file.

### 11. Low — §6's "static functions never cross files" is false when a `.c` file includes another `.c` file
What: lz4 compiles code from another `.c` file by including it: `lib/lz4hc.c` includes `lz4.c`; `tests/freestanding.c` includes `../lib/lz4.c` and `../lib/lz4hc.c`; `ossfuzz/fuzz_helpers.h` includes `lz4.c`; `lib/xxhash.h` includes `xxhash.c`. Static code does cross files this way, and the link closure cannot see it. `freestanding.c`'s closure is just 1 file. Moving `lib/lz4.c` to Rust leaves `freestanding.c` and `lz4hc.c` still compiling its C text.
Evidence: grep hits in the lz4 download; design-faithful run gives `tests/freestanding.c files 1`.
Suggested change: In §6 and §3.2, record "a `.c` included by another file" as a fact (from the include records). Show it beside the closure as a textual dependency. Exclude such a file from becoming a unit on its own without a warning.

### 12. Low — Assembly and prebuilt libraries are neither recorded nor set aside
What: The set-aside list (`.cc .cpp .m .go .rs`) leaves out `.s`, `.S` and `.asm`, the one kind of non-C source that does take part in a C link, and prebuilt `.a`/`.o`/`.so` files in the tree. A symbol defined in assembly shows as an outside symbol, and §3.4 then guesses a library for it. liblzg's `src/extra` holds `lzgmini_6502.s`, `lzgmini_68k.s`, `.js`, `.lua` and `.pas`, and the walk as written records none of them.
Suggested change: Set aside `.s/.S/.asm` and prebuilt libraries, with a count per folder. When an outside symbol may be defined in a set-aside assembly file or archive, say "may be defined in set-aside assembly in folder X" instead of guessing a library.

### 13. Low — The spike's point "the project links more than it needs" is not in the design's text
What: The map's file list for a tool will differ from what the project's own build links. lz4's Makefile links `lib/*.c` and `programs/*.c` (`lz4file.c`, and `util.c` when built without threads). The spike says to "say so where the map shows a tool". §3.5 and §6 do not.
Suggested change: Add a §6 line: "a tool's closure is what it needs, not what the build links. Extra linked files do not change what the program does, and are listed as unreached for this tool".

### 14. Medium — §4's test list would not catch the problems above
What: The current list covers only the benchmark, zopfli and the made-up project. The benchmark cases use quoted includes only (48 `"lib.h"`, no project header included with angle brackets), so findings 1 to 9 would all pass it. Each missing case can be a small committed fixture shaped like the download that showed it.
Suggested change: Add tests: a tool including `<proj.h>` from `include/` (1); two folders each holding `config.h`, and a project `util.h` beside a system one (2); a stated build whose `-D` adds a file and its pthread needs, with every closure shaped by a guess marked (3); liblzg's alternative decoder: the correct "keep `lib/decode.c`" reply is accepted, `lzgmini.c` accounted for, not listed as shared (4); a collision of an unneeded symbol inside one closure, reported (4); a fuzz driver of many: each fuzzer an entry, the driver never asked "which to keep" (5); a weak/strong pair not a duplicate, a weak undefined symbol not outside, common symbols (6); the `nm` reader run on recorded Mach-O and ELF output giving the same names without the underscore (6, no Linux machine needed); compile flags pinned and outside symbols tied to them (7); a map made under a different toolchain flagged (8); a cut-short walk producing no closures, an unreadable folder or non-UTF-8 file recorded while the walk goes on (9); the map run twice giving the same bytes, `root_hash` changing with a header but not a README (10); a `.c` that includes another `.c` (11); between-program duplicates (lz4's 14 helper names) listed but never asked about.

## What holds
- The link closures as the backbone: on both downloads the design-faithful run reproduced the spike's closures (lz4's tool 10 files; liblzg's `lzg` closure `checksum, encode, version`, the guide's list less `decode.c`). Closure files identical at -O0 and -O2 for every entry on both projects; only the outside symbols changed (finding 7).
- The spike's claims re-checked: 48/48 lz4 and 8/8 liblzg files compile alone with no flags; with `-DLZ4IO_MULTITHREAD` lz4's tool gains `programs/util.c` and 11 `pthread_*` plus `sysctlbyname`; `LZG_Decode`/`LZG_DecodedSize` fall inside `unlzg` and `benchmark`.
- Duplicates between programs are harmless and the design handles them (duplicates per closure); no lz4 closure pulled in a second `main` file (`mains_in 1` everywhere), so finding 4's gap is real but not seen on these two projects.
- Hidden visibility does not hide definers: `nm -g` lists hidden symbols as `T`.
- Symbols that macros create are handled (`DEF(made_by_macro)` shows as `T _made_by_macro`).
- Static functions are rightly left out of the closure (except finding 11).
- The confined walk itself: refuses symlink escapes and loops, sorts output, never reads contents, reports FIFOs, stops at a cap with `truncated` set. It suits step 1 once the skipped folders and limits are named (finding 9).
- "No source text", the 160-byte first error line, and "a file built twice with different flags appears once" (§6) are true as stated and agree with SCHEMAS' rules on hashes and timestamps, apart from defining `root_hash` (finding 10).

# Lens: security

# Security review of docs/PROJECT-MAP-DESIGN.md (draft 0 plus the §7 answers), untrusted input (reviewer: Opus, lens 2)

Two findings high, seven medium, two low. Every claim checked against the code. Three small harmless experiments run in scratchpad/review-security/t. closure.py not run (no claim needed it). Nothing edited in the repository.

## Findings

### 1. High: no rule says which flags may reach the compiler or the linker, and clang reads a `@file` argument as a list of extra options
What: Under the person's decisions, flags reach `cc` from three untrusted places: the download's `compile_commands.json`; flags a model proposes after reading the project's build files, which the person then confirms; the per-file `-D` and include-folder lists in the new `[target] files` form of `harness.toml`, which now sits inside the downloaded folder. The design says only "take its exact `-I` and `-D` flags and its working folder". It does not say in what form they are passed, so a plain implementation would copy a `-I` and its value as two separate arguments. Checked: clang treats any separate argument that starts with `@` as a file of options and reads it in. `cc -E -I @…/r.rsp x.c`, where `r.rsp` held `<dir> -DFROM_RSP=42`, printed `int v = 42;`. So `"-I", "@build/x.rsp"` in a hostile `compile_commands.json` lets the download add any compiler option: `-fno-integrated-as -B./tools/` (the driver runs the project's own `tools/as`); `-fplugin=` (loads the project's code into the compiler); `-o` or `-MF` (write anywhere the tool profile allows, including all of `/private/var/folders`). That is project code running inside the tool sandbox, and with no sandbox at all on Linux (finding 3). The same goes for a source path passed relative (a file named `@x.c` or `-lfoo.c`), and for the `directory` field if used as the working folder with no containment check.
Evidence: Design §3.1 step 4: "take its exact `-I` and `-D` flags and its working folder". §3.8: "a command in it that is not a C compile is ignored and counted" (says nothing about which arguments are kept). §7: "a model may read the build files and suggest them". §3.5: the "`[target] files` list (… with each file's include folders and `-D` flags)". Precedent: SCHEMAS "Trust boundaries": "`[oracle] extra_link_args` accepts ONLY `-l<name>` (`^-l[A-Za-z0-9_+.-]+$`)".
Suggested change: One flag grammar in §3.1 and §3.8, checked when the flags are read and again when `harness.toml` is loaded, whoever proposed them: only joined `-D<name>[=value]` with the name a C identifier, `-U<name>`, and `-I<dir>` whose folder is inside the root after resolving; nothing else, no value starting with `@` or `-`; always passed joined; every source and object path absolute, with `--` before the source; an entry whose `directory` resolves outside the root is ignored and counted; files that `compile_commands.json` names but the walk did not find are never compiled. §4 tests for `@file`, `-B`, `-fplugin`, `-o`, `-Xclang`, `-include` and a `directory` outside the root.

### 2. High: putting the ledger inside the download turns the download's own files into live inputs for the oracle
What: Decision 3 puts the ledger and targets at `<project>/migration/…`. Today the person copies only C files into RuHarness's `targets/`. Under the new layout three things inside a download start to act. (1) The project's `.cargo/config.toml` is loaded by every cargo build: cargo reads it from its working folder and every folder above; the oracle starts cargo in the target root (`Runner { cwd: root.clone(), … }`, crates/harness-oracle/src/lib.rs), now the project or a folder inside it, so `[build] rustc-wrapper = "./x"` or a `linker =` setting runs the download's program on every verify, migrate and perf build; sandbox.rs already expects this ("target-controlled build steps (a hostile `.cargo/config.toml` wrapper, a build script) must not see them"), and nothing refuses it. (2) A `migration/` folder shipped with the download becomes the ledger: it can hold a promoted crate with a `build.rs` (verify builds whatever `Cargo.toml` is on disk; it reads it only for `manifest_sets_panic_abort`); a ready-made `target/` folder that `prepare_target_dir` reuses ("if !target_dir.exists() { create … }"); green verdicts and `verified` statuses whose blake3 digests the author worked out; a `project-map.bins.json` that `map accept` would trust (§3.8 says the reply changes nothing until the check passes, but `accept` is a later command reading the stored file). All of this gets past the review gate and "behaviour recorded before the change". (3) A project's own legitimate `migration/` folder (database migrations) is silently skipped by the walk, breaking "Nothing is silently dropped". The design also never says which folder is a mapped tool's target root: if the project root, every tool shares one `migration/plan` and `facts`; if `<project>/migration/<tool>/`, the "paths relative to the project root" in `[target] files` need `..`, which the plan's path rule forbids ("clean relative paths (no `..`, not rooted …)", SCHEMAS).
Evidence: §3.8 "nothing of the project is ever executed" (holds for `map` itself, not for the targets it creates). Briefing §12.2: "writes confined to `migration/`, `target/`, and the build shim's output. Reject symlink escapes." What holds: `WriterLock::acquire` refuses a symlinked ledger folder; `write_atomic` uses an exclusive temp file plus rename.
Suggested change: `harness map` refuses when `<project>/migration/` already exists and was not created by the harness; record the first map's creation (the canonical root plus a random id) in user-level state outside the project, never a marker inside it; or use a harness-specific folder name and refuse when one is shipped. Run cargo with its working folder in a harness-owned folder outside the project and pass `--manifest-path`, so no project `.cargo/` is read; test with a `.cargo/config.toml` at the project root. `map accept` re-runs the link check rather than trusting the stored bins file. State the target root and the path rule for `[target] files`. Rewrite §3.8 so it no longer claims more than the design delivers.

### 3. Medium: on Linux there is no sandbox, yet the design says the map runs there and compiles by default
What: `sandbox_mode()` is `"none"` wherever `/usr/bin/sandbox-exec` does not exist. The design's CLI has no `--allow-unsandboxed`, and §6 says the work runs "wherever `cc` and `nm` exist". Unsandboxed, an `#include` or `#embed` of anything in the home folder is read; a compile error's first line can carry its words into the map inside the project (finding 4), then to the model and to anyone the project is pushed to.
Evidence: §6 "**Linux**: the walk and the check run wherever `cc` and `nm` exist; nothing here is macOS-only." §3.7 lists `harness map [--root DIR] [--json]` only. SCHEMAS: "Where no sandbox exists (`sandbox: none`), EVERY command that builds or runs target- or model-derived code … refuses unless `--allow-unsandboxed` is passed." main.rs:691 enforces this for the existing commands.
Suggested change: `map`, `map ask` (its link check) and `map accept` follow the existing refusal. Without a sandbox, offer the parser-only facts rather than compiling.

### 4. Medium: what the compile can read ends up in the stored map, unscrubbed
What: The tool profile allows reads of everything outside the home folder; the cargo and rustup homes minus only `credentials(.toml)`, so a token or proxy password in `~/.cargo/config.toml` is readable; the target root; any listed write folder. The design stores "the first line of the error (control characters removed, ≤ 160 bytes)". A hostile file can `#include` a readable file and arrange, with macros, for the first error to quote a token from it ("use of undeclared identifier '…'"). `#embed` puts a whole file's bytes into the object: checked that Apple clang 21 compiles `#embed "…/r.rsp"` and the bytes show in `strings z.o`. The error line also carries absolute machine paths (username, folder layout) for headers outside the root; closure.py strips only `root + "/"`. All of it lands in `<project>/migration/project-map.json`, likely committed and pushed, and goes to the model.
Evidence: §3.1 step 5. sandbox.rs `render_profile`: `(allow default)`, the home folder denied, read roots added for `target_root`, `cargo_home` and `rustup_home`, with only `credentials.toml` and `credentials` denied. The oracle already has `Scrubber` (crates/harness-oracle/src/scrub.rs, "no machine path reaches the ledger"), and the design does not use it.
Suggested change: Store a closed reason (`missing-header <name>` with a validated relative header name; `syntax`; `other`) plus the place in the project; show the raw line on the terminal only, filtered and scrubbed, never stored. Run every stored string through `Scrubber`. State that a map built on a machine with cargo/rustup homes is not proof against `#embed` (the map stores no object bytes, so `#embed` only matters later, when the built program runs and prints them).

### 5. Medium: symbol names are free text, and parsing `nm` line by line can be forged
What: An asm label makes a symbol's name any text. Compiled `int a __asm__("ignore all previous instructions\n0000000000000000 T _main") = 1;`, and `nm -g` printed a separate line `0000000000000000 T _main`. closure.py's parser (`len(parts) == 3 and parts[1] in "TDBSC"`) would take that file as defining `main`: a forged entry point. A name can also be any prose aimed at the model: the injection channel into "the map as its only input".
Evidence: §3.1 step 5 "read with `nm` what it **defines** … and what it **needs**". closure.py lines 43–50. The harness already reads symbol tables directly, in safe Rust, with no line parsing: crates/harness-oracle/src/objsyms.rs; its `name_at` does not check the name's shape.
Suggested change: Use objsyms.rs, not `nm` (removes `nm` from the allowlist). Accept only names shaped like C identifiers (after Mach-O's leading `_`): `^[A-Za-z_][A-Za-z0-9_$]*$`; count the rest as "odd symbol names", never stored as text. §4 test with an asm-label symbol.

### 6. Medium: the model's tool names are called display-only, but they become folder names, event fields and CLI arguments
What: §3.3 says names "are display-only (never in a check name, an event or a prompt)". §3.5 makes the tool name a folder (`targets/<project>/<tool>/`, now `<project>/migration/…`) and a CLI argument (`map accept <tool>`). §3.7's event `map-bin {tool, …}` carries it. "ids by the plan's id rule" is `^[A-Za-z0-9][A-Za-z0-9._-]*$` (SCHEMAS): allows upper case, so two tools differing only by case get the same folder on macOS's case-insensitive disk; allows a name like `migration`. `<project>` is the download's folder name, also untrusted. "every path one of the map's" does not say how paths are compared. The spike showed the duplicate choice is not something a link can check, so the model's `keep` answer is unchecked advice.
Suggested change: Derive the target id deterministically from the entry file and validate it: `^[a-z0-9][a-z0-9_-]{0,63}$`, unique, not reserved, not equal to another ignoring case. Keep the model's name display-only. Paths: exact byte membership in the map's list ("lookup, never path sanitisation", as SCHEMAS says for `src/logic.rs`). Every duplicate choice shown to the person with both definers and confirmed.

### 7. Medium: what the person reads at the review gate can be forged, and `--json` does not escape what its comment says it does
What: Plain output: the CLI's filter keeps newlines (`terminal_safe` uses `unsafe_to_show(c) && c != '\n' && c != '\t'`, crates/harness-cli/src/report.rs); `map` prints paths and error lines, and on macOS a file name can contain a newline, so a download can print a fake extra line such as "1 tool, 0 duplicates" exactly where the person decides. `--json` uses `serde_json::to_string`, which escapes only `"`, `\` and U+0000–U+001F; DEL, the C1 controls (U+0080–U+009F, among them CSI) and bidi characters pass through raw, yet the code comment says "The JSON mode escapes them already". Events: the new events put raw paths and symbols in them (`map-tool {entry, files, outside, duplicates}`), contrary to the features rule in SCHEMAS: "only ids and closed reasons reach checks, prompts, events or harness-mcp". Two filters: the cockpit's (crates/harness-tui/src/display.rs) turns a newline into `?`; the CLI's does not; "display-filtered everywhere" means two different filters today.
Suggested change: Map lines print each untrusted string with newlines and tabs filtered too, one string per line. Emit `--json` with every `unsafe_to_show` character escaped as `\uXXXX`. Events carry indexes into the map plus closed reasons, not raw names.

### 8. Medium: "escaped for HTML" is the wrong rule for the export the design describes
What: §3.9 proposes "a single self-contained HTML file (… the graph data embedded)". Data embedded in a `<script>` block is broken out of by `</script>` or `<!--` inside a JSON string, whatever HTML escaping is done. Names later inserted with `innerHTML` are a second hole. "No network" is not enforced by anything if one string gets through. The file would be written into the hostile project folder, where a shipped `migration/project-map.html` could be opened in its place.
Evidence: §3.9: "Untrusted names (paths, symbols, the model's tool names) are escaped for HTML as the cockpit display-filters them for the terminal."
Suggested change: Embed the data as JSON with `<`, `>` and `&` written as `<`, `>` and `&`, insert names only with `textContent`; add a CSP meta (`default-src 'none'; script-src 'sha256-…'; style-src 'sha256-…'`) so the browser enforces "no network"; write the file with an exclusive create, or outside the project.

### 9. Medium: nothing bounds memory, disk or total time, and a large file is read whole
What: Briefing §12.2 asks for "CPU/memory/time limits". Only a wall-clock timeout per child exists; no `setrlimit` anywhere in the crates. `#embed "/dev/zero" limit(4000000000)`, or a large initialized array, writes a multi-gigabyte object. An `#include` of a FIFO or of `/dev/zero` holds a compile for the full 120 s. 20 000 files × 120 s is about 27 days. In the harness process itself (not sandboxed, no timeout) the scanner reads every `.c`/`.h` whole (`std::fs::read_to_string(abs)`, harness-scan/src/lib.rs:164) with `walk::Limits::default()`, which "bounds nothing"; the walk's limits are a file count and a depth, never bytes.
Suggested change: Cap each file's size before parsing or compiling (recorded as "too large"). Limit file size and memory on the compile child. Set a total time budget for `map`. Delete each object as soon as its symbols are read. Put objects in a fresh harness-owned temp folder (as the features map does), never inside the project.

### 10. Low: object names can collide, and "links refused" is not what the walk does
What: closure.py names objects `rel.replace("/", "__") + ".o"`, so `a/b.c` and `a__b.c` write the same object; one file's symbols are attributed to the other. The design says "links refused as today"; in fact walk.rs follows links that stay inside the root ("one that resolves outside the walked directory … is left out"), so one file can appear twice under two paths and create a fake duplicate. The compile follows any link or absolute `#include`, limited only by the sandbox, so `root_hash` does not cover headers outside the root that a compile read.
Suggested change: Name objects by their index in the map. Fix the wording to say what the walk does. Record, per file, whether it included anything outside the root.

### 11. Low: `--root` set to the home folder (or above it) opens the whole home folder to every compile
What: `render_profile` adds `target_root` to the read roots unconditionally. It guards TMPDIR ("never a TMPDIR that is the home folder or holds it") but not the target root. A `harness map` run with the wrong working folder would compile every `.c` it finds with the whole home folder readable.
Suggested change: Refuse a root that is the home folder, contains it, or contains the cargo or rustup homes. §4 test.

### Missing tests
§4 has no hostile-input cases beyond "control characters". Add at least: `@file` and `directory` in `compile_commands.json`; a project `.cargo/config.toml`; a shipped `migration/`; an asm-label symbol; a file name containing a newline; `--root ~`.

## What holds
- Hostile folder names cannot break the sandbox profile: `sbpl_string` refuses `"`, `\`, control characters and relative paths rather than escaping them.
- The tool profile's basic limits are sound: network denied, reads under the home folder denied except the listed roots, cargo credentials denied; writes limited to the listed folders, temp and three devices; `NO_STARTS_THROUGH_THE_SYSTEM` stops launchd starting programs for the compile.
- Child processes are run carefully (exec.rs): argv arrays, never a shell; environment cleared to a fixed list; `stdin(Stdio::null())`, so `#include "/dev/stdin"` reads nothing; each child in its own process group, killed whole at the timeout; output capped at 64 MB.
- The allowlist only ever allows: a project's `harness.toml` can only shorten the list.
- The walk refuses links that lead out of the root, links that point nowhere, and FIFOs and devices (`Skip::NotRegular`).
- The scanner's include resolution stays inside the project (`resolve_quoted_include` over `scanned`).
- Ledger files are read and written defensively: a symlinked ledger folder refused at lock time; writes through an exclusively created temp file and a rename; `read_regular` refuses links, never blocks on a FIFO, stops at a size bound. The map files should be read back through it.
- harness-mcp has one fence (crates/harness-tui/src/fence.rs): every path and symbol wrapped `{"untrusted": …}` with a size cap.
- Guessed libraries come from a fixed table, and `extra_link_args` is already limited to `-l<name>`.
- The project's own build is never run, and the map step never runs the programs it links (§3.4, §6).
- The model's reply is closed in shape (fixed kinds, map paths only, a refused reply changes nothing); it needs only finding 6's id and path rules and finding 2's re-check at accept.

### High

**1. The reply format has no answer for the spike's entry kinds, so the fuzz driver becomes a "which one?" question that any answer passes.**
- What: The walk only finds `main`. The reply's kinds have no fuzz target and no "driver of many". lz4's `ossfuzz/standaloneengine.c` therefore becomes a closure with a 10-way duplicate of `LLVMFuzzerTestOneInput`, and the model is asked which definer to keep. If the model calls the driver a `tool` and keeps any one fuzzer, the program links, the check passes, and a bogus tool is offered to the person. The design's closure step (§3.1 step 7) also lacks the spike script's rule that a file defining `main` is never pulled into another closure. Without that rule, a closure that needs a helper from another tool's file gets a duplicate `main` question.
- Evidence: DESIGN:65 "Every file that defines `main` is a candidate tool." DESIGN:111 kinds `tool | test | example | benchmark | other`. DESIGN:112 "for each duplicate: which definer to **keep**". INVESTIGATION:122–124 "it is a driver linked once with each fuzzer, not a program … the question for the model is 'what is this?', not 'which one?'". INVESTIGATION:87–88 "a file that defines `main` is never pulled into another closure". lz4 `ossfuzz/Makefile:69` links fuzzers with `$(CXX) … $(LIB_FUZZING_ENGINE)`, so they are not plain C programs.
- Suggested change: The walk classifies entry points itself, without a model: `main`; `fuzz` (defines `LLVMFuzzerTestOneInput` and no `main`); `driver` (a `main` whose needed symbol is defined by two or more entry files). Add `fuzz` and `driver` to the closed list of kinds. Never offer `driver` or `fuzz` entries as tools, and never link them in §3.4. Add the never-pull-a-`main`-file rule to §3.1 step 7. Only a duplicate inside one closure, whose definers are not entry files, becomes a question for the model.

**2. "cannot tell" leads nowhere, and a guessed definer passes the check.**
- What: §3.3 pairs every duplicate with a `keep` choice and gives `cannot tell` only as a reason. So a model that cannot tell must still pick one. On liblzg either choice links (`decode.c` or `lzgmini.c`), so §3.4 accepts the coin flip as checked. This is exactly the case the model step exists for.
- Evidence: DESIGN:112–113 "which definer to **keep**, and why in one line (`platform: unix`, `alternative implementation`, `cannot tell`)". INVESTIGATION:139 "so `unlzg` and `benchmark` are each ambiguous between the two — and either choice links". DESIGN:123 links "with the duplicates resolved as the reply says".
- Suggested change: The answer to a duplicate is `keep: <definer>` or `undecided`. The reason is a closed list; any free-text line is capped, single-line and shown only as the model's words. The harness links every choice (usually two). When more than one choice links, the check cannot decide: the tool is shown as "held: the model picked X; linking cannot tell X from Y", and the person chooses. `undecided` always goes to the person. Ask one question per set of definers, not per symbol (liblzg's `LZG_Decode` and `LZG_DecodedSize` share one pair of files). Say whether a choice applies to one tool or to the whole project.

### Medium

**3. The design claims more for the link check than it proves, and the person is never told.**

It does not prove: the entry's kind; the right definer when several link (finding 2); the right build configuration; that the program exports the same symbol names as the project's own build; that the file list matches the project's build; that the program runs. lz4 shows a second flag the link cannot see. `-DXXH_NAMESPACE=LZ4_` renames every xxhash export, the spike's walk without flags leaves it out, and the closure still links.
