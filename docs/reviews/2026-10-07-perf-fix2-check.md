- Evidence: Reasoned trace. measure.rs select() pushes Selected::NotVerified with no position check. Lines 1028-1062 turn every NotVerified unit and every set-up unit into a LeftOut. Store::put (measure.rs:2245) calls res::write_program(...)?, which calls check_rows, which calls check_inputs, which calls at_most(left, MAX_UNITS, "left_out")? (results.rs:886). The only limit on plan size is Slot::name (build.rs:115), reached at measure.rs:969 only for a Ready unit whose crate built and whose replaces matched. **[medium] The caps do not stop the growth on parse that the item names, and they do not bound what a file hands on** — `crates/harness-core/src/perf/results.rs:586` (item 3)

- What: The item exists because 'a forged file otherwise grows many times on parse'. The caps are checked only after serde has built the whole file, and it is built twice: parse_json first parses all of it into a serde_json::Value to read schema_version, then parses it again typed. So a refused file still grows in memory exactly as it did before the fix. The rows lists (c_alone, as_it_stands, a unit file's rows) are not capped either, and MAX_REPLACES (65 536 per row) is about as large as a 4 MiB file allows anyway. So a forged file within every cap can still hold about a million entries and be accepted and handed on. The new SCHEMAS sentence 'The caps bound what the reader accepts and hands on' overstates this. The fix does close the quadratic once-each walk over units and left_out, which is now at most 999 entries per list.
- Evidence: Probes in a scratch copy at c92f6ec, measured with /usr/bin/time -l on the test binary (an empty run peaks at about 7 MB). (1) A 4 194 096-byte program.json with 97 526 left_out entries was refused ('left_out holds 97526 entries, at most 999') after 705 ms, with an 85 MB peak footprint. (2) A 4 MiB file with an unknown field holding 1.4 million empty arrays was refused for the unknown field, with a 52 MB peak. All of that came from the Value pre-parse, because the typed parse stops at the unknown key. (3) A 3 938 264-byte units/u001.json with 15 rows of 65 536 one-letter replaces was accepted: 983 040 strings handed on, 55 MB peak. The cockpit's perfread (perfread.rs:193) keeps every plan unit's parsed file at once, so each forged unit file adds that much.
- Suggested fix: Cap the rows lists at workloads::MAX_WORKLOADS (16); Store::put already prunes rows to the workloads file, so that is honest. Read schema_version through a small struct that has only that field, so the rest is skipped without being built, instead of parsing the whole file into a serde_json::Value. If growth during the parse itself must stop, check list lengths while deserializing: a deserialize_with visitor that refuses after N elements, with no new crate. Reword the SCHEMAS sentence to match what is enforced.
